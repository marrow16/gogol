The Captured Patterns popout is available from the main menu.

Captured patterns are patterns that have been obtained from a grid state - see edit mode.
Briefly, in edit mode, just mark an area of the grid using Shift+← Shift+→ Shift+ ↑  Shift+ ↓  keys and then press ↩ to capture. Multiple patterns can be captured in a single edit session.

Once a pattern has been captured from grid edit, it will appear in the dropdown.
You can also add captured patterns from external sources by copying the rle content and pressing the Paste RLE button in this popout.

Having selected a captured pattern from the dropdown - use the view modes:

Preview

Shows a preview image of the captured pattern.

Use the Identify button to search for the same pattern in currently loaded patterns. All rotations and mirrors of the pattern will be searched - and if the With phases is checked, GoGoL will run a short simulation on the pattern to detect transitional phases to search for.
On identify, the number of hashes searched and whether the pattern was found is displayed. If the pattern is found, a link is displayed and clicking on that link will take you to the pattern.
Note: On first use of identify, GoGoL must build an in-memory hash index for loaded patterns - this can take a couple of seconds for large libraries (i.e. >4000 patterns)

Metadata

Shows editable metadata for the captured pattern.

Edit the metadata as required and then press Save button to save the pattern to an .rle file. Check the Add to library option to also add it to the patterns library.

Use the Remove button to remove the currently selected captured pattern or press Clear button to clear all captured patterns.
The Grid Recipes popout is available from the main menu.

Select an existing grid recipe from the dropdown, or enter the path to a recipe .json file. Alternatively, use the ... button to open the file finder.

Selecting a recipe file registers it for use by GoGoL. The recipe is not loaded, parsed or validated at this point - the file is only read when the recipe is run.
Because recipes are loaded on demand, the recipe file can be edited and re-run without restarting GoGoL.

Press the Run button or press ⌥G to execute the selected recipe. If the recipe cannot be loaded or contains an error, the error will be displayed.

Use Save as RLE button to execute the recipe and save the resulting grid as an RLE file.

For details of the Grid Recipe JSON format and available operations, see the Grid Recipes Reference.
The Instrumentation popout is accessed from the main menu.
Instrumentation provides tools for analysing and recording the behaviour of the grid. Each instrument can be independently enabled or disabled using its checkbox.

The following tools are available:

Repeat Detect
When enabled, monitors successive generations looking for a grid state that has occurred previously. When a repeat is found, First and Repeat show the generations containing the matching states, and Period shows the number of generations between them.
Also, when a repeat is detected for the first time, the running simulation will stop and the repeat found is notified on the statusbar
Reset
clears the current repeat detection history.
Save Report
saves a report of the detected repeat as a .json file in the documents/GoGoL folder.
Record
When enabled, retains previous generations, allowing the simulation to be stepped backwards and for animations to be saved.
Steps recorded
shows the number of generations currently retained.
Skip back by
determines how many generations are skipped when using the skip-back control.
Press ⌥⌫ or use button on statusbar
Reset
to discard the current recorded history.
Save Animation
to save the recorded steps as an animation - Gif or Mp4 file.
Note: The Mp4 option is only available when ffmpeg is installed. [see https://ffmpeg.org/]
WARNING: Saving animations above 1000 or so steps can produce very large files!
Heat Mapping
Accumulates cell activity over successive generations that can be visualised as a heat map image.
Type determines the information accumulated:
• Activity - 
how frequently each cell changes state.
• Age - 
the current age of alive cells.
• Births - 
how frequently a cell becomes alive.
• Freshness - 
how recently each cell changed state.
• Longevity - 
the maximum continuous age ever attained by each cell.
• Occupancy - 
how many generations each cell location has been alive.
• Phase Parity - 
distinguishes activity occurring on odd and even generations.
• All - 
collects all the above heat map measurements.
Reset
to clear the accumulated heat map data.
Reveal
to display the heat map image.
Or press ⌥H. See also heat map display
Save Image
to save the heat map image as a .png file in the documents/GoGoL folder.
If All is active - images for each heat map type are saved.
The Shortcuts popout is available from the main menu.

Shortcuts are named macros that can execute an action or series of actions in GoGoL.

Select an existing shortcut from the dropdown, or enter a new name to create a new shortcut.

If the shortcut name matches a keyboard key, it can be invoked by pressing ⌥ plus that key. For example, a shortcut named A can be invoked by pressing ⌥A - likewise, a shortcut named F1 can be invoked with key ⌥F1
Note: Shortcut keys can override can override GoGoL assigned keys.

Having selected or created a shortcut, use the Actions area to edit the actions associated - each action on a new line. See Shortcuts Actions Reference.

During actions editing, any syntax errors in the actions will be displayed. Syntax errors are only a validation of recognised actions and expected operands for those actions - not whether values are valid at shortcut run.
Syntax errors do not prevent the shortcut being saved and/or run.

Errors encountered during shortcut run are logged in the file: [user]/Documents/GoGoL/errors.log
Shortcuts can execute javascript using the following action:
javascript:filename
• 
where filename is either an absolute path - or is taken as a relative path from [user]/Documents/GoGoL/
• 
the script is compiled as ECMAScript 5.1 - any compilation errors are logged to [user]/Documents/GoGoL/errors.log
• 
the script is not cached - it is compiled from the file each time the shortcut is run. Therefore, between shortcut runs, the script can be modified with external editors.

A Grid Recipe is a JSON document that describes how to construct an initial Game of Life grid.

Recipes are executed on demand and are not preloaded or cached. A recipe can be edited in any text editor and re-run immediately without restarting GoGoL.

Grid recipes can be loaded from the Grid Recipes popout in the main menu.
Once a recipe is selected in the popout, it can be executed by pressing ⌥G or by clicking the Run button in the popout.

JSON Structure

The overall structure is defined as:
{
  "name": "Example",
  "grid": { ... },
  "vars": { ... },
  "patterns": { ... },
  "do": [ ... ]
}
Note: Any unknown JSON properties are ignored.
• grid property
The optional grid property configures the overall grid (if this property is not specified, then the current grid settings are used)
{
  "grid": {
    "height": 100,
    "width": 100,
    "rule": "B3/S23",
    "wrap_mode": "toroidal",
    "boundary_mode": "dead"
  }
}
All properties are optional - properties omitted (or null) default to the current grid setting.
• vars property
Variables store numeric values or binary patterns.
{
  "vars": {
    "my-pattern": "0b000101",
    "my-num": 10
  }
}
The property name, e.g. `my-pattern`, denotes the var name for later use.
When using a string to denote the initial value:
• 
"0b101" (binary notation) denotes 5 and a specific width (when used as a pattern) of 3 cells.
• 
"0b000101" (binary notation) denotes 5 and a specific width (when used as a pattern) of 7 cells.
• 
"0o07" (octal notation) denotes 7 and a specific width (when used as a pattern) of 6 cells.
• 
"0x0E" (hexadecimal notation) denotes 14 and a specific width (when used as a pattern) of 8 cells.
• 
"0xE" (hexadecimal notation) denotes 14 and a specific width (when used as a pattern) of 4 cells.
• 
"127" (decimal notation) denotes 127 and the width (when used as a pattern) will be the minimum number of bits to represent that value.
Also, the string can be prefixed with various flags:
• 
"alt:"|"alternate:"
alternate cells on each successive placement.
• 
"rot:"|"rotate:"
rotate cells on each successive placement according to Y position.
• 
"fw:"|"fullwidth:"|"full-width:"
the pattern is built to fill the grid width.
• 
"fh:"|"fullheight:"|"full-height:"
the pattern is built to fill the grid height.
A variable can be placed on the grid (as the derived binary pattern) by referencing its name in a `place` property, e.g.
{
  "do": [
    {
      "place": "my-pattern"
    }
  ]
}
• patterns property
Patterns can be:
• 
External rle files
{
  "patterns": {
    "beacon": {
      "filename": "beacon.rle"
    }
  }
}
Note: relative filenames are relative from the recipe json file.
The recipe will error if the file cannot be found or cannot be decoded.
• 
Inline rle definitions
{
  "patterns": {
    "block": {
      "rle": "2o$2o!",
      "width": 2,
      "height": 2
    }
  }
}
Note: the width and height properties are mandatory when rle property is specified.
The recipe will error if the `rle` cannot be decoded.
• 
Reference to a name in the current pattern library
{
  "patterns": {
    "glider": {
      "name": "Glider"
    }
  }
}
Or abbreviated form:
{
  "patterns": {
    "glider": "Glider"
  }
}
The recipe will error if the name cannot be found in the current pattern library.
• do property
Contains an array of the actual instructions for placing items on the grid.
{
  "do": [
    {
      "place": "name",
      "at": { ... },
      "move": { ... },
      "repeat": 1,
      "rotate": 1,
      "do": [ ... ],
      "var_operations": [ ... ]
    },
    ...
  ]
}
All properties within a do object are optional.
• do.place property
The name of the variable or pattern to place - referenced to a name in vars/patterns within in the recipe.
If the place is omitted or null - nothing happens, but nested do instructions are still carried.
If the name does not resolve to a variable or pattern, the recipe will error.
• do.at property
Defines an absolute placement position on the grid, e.g.
"at": {
  "x:": 0,
  "y": 0
}
Both the x and y properties are optional - if not specified, the current position is used.
• 
x can also be specified as "gw", "gridwidth" or "grid-width" to denote right-most position.
• 
y can also be specified as "gh", "gridheight" or "grid-height" to denote bottom-most position.
• do.move property
Defines a relative position to the current position, e.g.
"move": {
  "x:": 0,
  "y": 0,
  "when": "before|after"
}
All properties are optional.
If the x/y properties are omitted or null then the current position for that part is unaffected.
The x and y properties are relative to the current position, so can be positive or negative. They can also be specified as a string - one of the following:
• 
"lw" is the width of the last placed pattern/var
• 
"lh" is the height of the last placed pattern/var
• 
"-lw" is the negative width of the last placed pattern/var
• 
"-lh" is the negative height of the last placed pattern/var
Using the above tokens, the dimension can also be adjusted e.g.
• 
"lw+5" is the last width plus 5
• 
"lh++" is the last height plus 1
The `when` property controls when the move happens - i.e. before or after the placement. If omitted or null it assumes before.
• do.repeat property
Is the number of repeats (after the initial placement).
This can also be specified as a string - one of the following:
• 
"gh"|"gridheight"|"grid-height"
repeats to fill the remaining grid height.
• 
"gw"|"gridwidth"|"grid-width"
repeats to fill the remaining grid width.
• do.rotate property
Is the number of 90 degree rotations for the placed pattern. Values greater than 3 are taken as modulus 4.
• do.do property
Contains nested instructions.
• do.var_operations property
Are operations to perform on the currently placed var (and only relevant when placing a var).
{
  "place": "my-var",
  ...
  "var_operations": [
    {
      "when": "before|after", // defaults to after
      "shift_left": 1,
      "shift_right": 1,
      "rotate-left": 1,
      "rotate-right": 1,
      "increment": 1,
      "decrement": 1
    },
    ...
  ]
}

Use the Sizing/Wrapping/Boundaries popout from the main menu to adjust various settings on grid sizing and behaviour.

Use the Grid size Width and Height inputs to set the desired size for the grid - the grid size is only updated by pressing the Resize button.
Press the Fit screen button to resize the grid to fill the available screen size (according to current cell size and zoom rate).
The Keep cells checkbox is used to determine whether the grid alive/dead cells are preserved during resizing.

Wrapping mode determines how cells at the edges of the grid interact with cells on the opposite edges:
• None - 
grid edges do not wrap.
• Horizontal - 
left and right edges wrap around to each other.
• Vertical - 
top and bottom edges wrap around to each other.
• Toroidal - 
all grid edges connect to their opposite edge.
When grid edges are not wrapped, the Boundary mode determines how cells beyond those edges are treated. They may be considered either Dead cells or Alive cells when calculating the neighbours of cells at the grid edge.

The Cell size input determines the size of each grid cell in pixels (1–32). Updating this value will take immediate effect.

Randomize % input is used to determine the percentage of alive cells when randomizing the grid (from the main menu or pressing ⌥R).
Note: The randomize % setting only determines probability of alive cell - not overall grid density. To specify an overall random density, create a shortcut using action randomize-population.
GoGoL is an interactive cellular automata explorer, built around Conway's Game of Life (wikipedia) and the wider family of Life-like rules.

It provides tools for creating, running and analysing cellular automata; experimenting with rules and patterns; recording and identifying patterns; and visualising behaviour through instrumentation and heat maps.

GoGoL is intended as much for experimentation and discovery as for simply watching cells live and die.

Advanced - VariablesShortcut variables:
• 
Add persistent, reusable state to shortcuts. They can be used to store values, construct or modify values over a sequence of actions, and pass those values to and from other shortcut actions. Variables are shared between shortcuts, including shortcuts invoked using call-shortcut, and their values are retained between application runs.
• 
Store values as text. When a variable is used, its value is interpreted according to the type required by the action. This allows variables to supply text, numbers, colours, rule permutations, and other supported values without variables themselves having a fixed type. If a value cannot be converted to the required type, the action/operation is ignored.
• 
Values may include substitutions from other variables and format tokens, allowing values to be constructed dynamically from the current application state. Arithmetic and bitwise operations provide further manipulation where appropriate.
• 
Can control repetition and stepping, change application settings, construct filenames or colours, manipulate rules, and support more complex macro-like sequences without requiring an expression language.

Declaration

To declare (set) a variable as an action:
variable:name=value
where:
name 
is a non-empty string name for the variable
value 
is the initial value for the variable - which may include format tokens and/or references to other variables
Note: Variable names are case-sensitive, must start with a letter ('a'-'z' 'A-Z') and may contain characters: 'a'-'z', 'A-Z', '0'-'9' or '_'

Manipulation

Existing variables can be manipulated using the following basic syntax:
variable:name operator operand
where operator can be:
+= 
adds the operand value to the named variable value
If both the named variable and operand are integer values then an arithmetic addition is performed - otherwise a string concatenation is performed.
Examples: 
variable:myvar=1
variable:myvar += 2
log:$$myvar is now $myvar
variable:myvar +=foo
log:$$myvar is now $myvar
-= 
subtracts the operand value from the named variable value
Both the named variable and operand must be integer values - otherwise no operation is performed.
Example: 
variable:myvar=3
variable:myvar -= 2
*= 
multiplies the named variable value by the operand value (and stores result back to the variable)
Both the named variable and operand must be integer values - otherwise no operation is performed.
/= 
divides the named variable value by the operand value (and stores result back to the variable)
Both the named variable and operand must be integer values - otherwise no operation is performed.
&= 
performs bit AND of the named variable value and operand value (and stores result back to the variable)
Both the named variable and operand must be integer values - otherwise no operation is performed.
|= 
performs bit OR of the named variable value and operand value (and stores result back to the variable)
Both the named variable and operand must be integer values - otherwise no operation is performed.
^= 
performs bit XOR of the named variable value and operand value (and stores result back to the variable)
Both the named variable and operand must be integer values - otherwise no operation is performed.
++ 
(no operand) increments the named variable value
The named variable must be an integer value - otherwise no operation is performed.
-- 
(no operand) decrements the named variable value
The named variable must be an integer value - otherwise no operation is performed.

Usage

Variables may be used as format tokens by prefixing the variable name with $. The variable reference is replaced with its current value before the action is performed.
Example: 
variable:steps=100
step-ahead-by:$steps

Variable references may also be embedded within other text and combined with other variables or format tokens
Example: 
variable:R=AA
variable:G=00
variable:B=80
variable:rgb=#$R$G$B
cell-color-alive:$rgb

Clearing

Variables can also be individually or collectively cleared.
clear-variable:name 
clears the named variable.
clear-variables 
clears all variables.
clear-variables:name;name,... 
clears the named variables.
Note: Clearing a variable that has not been defined has no effect and causes no error.

Logging

For shortcut debugging assistance, all current variables can be logged with:
log:%variables
The current variables, along with their values, will be written to the output.log file.
Advanced - Conditionals/Stopping/BreakingAction if provides simple conditional control over actions execution. Subsequent actions are only executed when condition evaluates to true.
Example: 
if:%MM == 9,log:"it is September"
logs the message if the current month is September.
Example: 
if:%MM >= 6,if:%MM <= 8,log:"it's summer!"
logs the message only if it's summer.
Action while provides simple iterative conditional control over actions execution. Subsequent actions are only executed while the condition evaluates to true.
Example: 
variable:max=10
variable:i=0
while:$i < $max,log:$i,variable:i++
logs the incrementing value of $i while it is less than the maximum.
Stopping and breaking provide simple conditional control over shortcut execution. A shortcut, called shortcut, or repeat loop can be terminated when a specified condition becomes true.
stop-if 
stops the entire shortcut execution. This applies regardless of where it occurs, including within a repeat loop or a shortcut invoked using call-shortcut.
Example: 
stop-if:%MM > 9
stops the entire shortcut execution if the current month is greater than September
break-if 
stops only the current execution scope. Within a repeat loop it breaks from that loop, allowing execution to continue with the following action. Within a called shortcut it stops that shortcut and returns to its caller. At the top level it stops the current shortcut.
Example: 
variable:perc50=%grid-width
variable:perc50 *= %grid-height
variable:perc50 /= 2
break-if:%population < $perc50
stops the current shortcut scope if the grid population is less than 50%
Notes:
• 
Allowed comparators are == (equals), != (not equals), > (greater than), < (less than), >= (greater than or equals) and <= (less than or equals)
• 
If both values resolve to integers then a numeric comparison is evaluated - otherwise a case-insensitive string comparison is evaluated.
• 
Both compared values can be explicit, format tokens or variables.
• 
Additionally, the are special pre-defined conditions:
rule-collected 
evaluates to true if the current rule is collected.
!rule-collected 
evaluates to true if the current rule is not collected.
variable-exists:name 
evaluates to true if the named variable is defined.
Example: 
break-if:variable-exists:foo

evaluates to true if the named variable is not defined.
variable-exists-n:name 
evaluates to true if the named variable is defined and is numeric.
!variable-exists-n:name

Example:

Meta Rules normative syntaxThe following provides the normative reference for Meta Rules syntax:
meta-rule     = predicates

predicates    = predicate ["," predicate]...
predicate     = rule | all-of | any-of | none-of | one-of

all-of        = "AllOf(" predicates ")"
any-of        = "AnyOf(" predicates ")"
none-of       = "NoneOf(" predicates ")"
one-of        = "OneOf(" predicates ")"

rule          = rule-part ["/" rule-part]...
rule-part     = birth
              | survival
              | and-rule
              | or-rule
              | xor-rule
              | permutation
birth         = "B(" conditions ")"
survival      = "S(" conditions ")"
and-rule      = ("A(" | "&(") conditions ")"
or-rule       = ("O(" | "|(") conditions ")"
xor-rule      = ("X(" | "^(") conditions ")"
permutation   = "P(" ranges ")"

conditions    = condition ["," condition]...
condition     = required
              | forbidden
              | excluded-combination
              | cardinality

required             = "+" digits
forbidden            = "!" digits
excluded-combination = "-" digits
cardinality          = "#" integer ".." integer ":" digits

digits               = digit...
digit                = "0" | "1" | "2" | "3" | "4" | "5" | "6" | "7" | "8"

ranges               = range ["," range]...
range                = integer | integer "-" integer
Notes:
•
Tokens are case-insensitive.
•
Whitespace may appear freely between tokens.
•
Within a rule, B(...), S(...), A(...), O(...), X(...) and P(...) may each appear at most once.
•
Digits within a condition are unordered.
•
Duplicate digits are not ignored - and will cause errors if repeated.
•
Integers can be specified in base 10, binary (e.g. 0b11111111) octal (e.g. 0o377) or hexadecimal (e.g. 0xFF)
•
Line comments // are allowed - block comments /* are not allowed
